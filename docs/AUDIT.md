## Rejected or unsupported recommendations

- **Speculative Shagun RPC/policy suggestions are not automatically defects.** Those suggestions did not establish a reproducible Shagun authorization failure; this does **not** negate the confirmed BihariBhojan API exposure below. Retain parameter validation, role-specific grants and RLS; do not widen policies to mask API-configuration issues or present a historical missing-schema error as a fresh failure.
- **Repeated Auth checks are not, by themselves, an authorization bug.** `getAdminContext` uses request-only memoization, while mutations/private endpoints reauthorize independently. Removing those checks would weaken the boundary.
- **Do not add cross-request caching of authorization or privileged dashboard/preview responses as a speculative optimization.** Public versioned snapshots have a live anonymous visibility check first; that is not permission to cache private access decisions.
- Do not report “all eight exploration bugs fixed” or “no security issues.” Only the resolutions above have a stated basis. SQL installation and Production key storage are complete; hosted runtime acceptance still requires independent evidence.

## CRITICAL shared-project API exposure — confirmed, not changed here

Historical SQL inspection found anonymous/authenticated SELECT privileges and disabled RLS on existing BihariBhojan `public` tables. The recorded anonymous probes **`HEAD /rest/v1/Order?select=id&limit=0`** and **`HEAD /rest/v1/ContactMessage?select=id&limit=0`** both returned **200**. This established managed API reachability, not merely catalog risk; current approval status remains in [VERIFICATION.md](VERIFICATION.md). **No customer rows were retrieved**; do not retrieve any to demonstrate impact. Empty baseline tables do not protect future customer records.

The public publishable key was momentarily visible in the browser UI, used only in browser memory and hidden before tool results; its value was not printed or returned to the model. **Private/backend secrets were not read or revealed.** The probe did not modify the shared baseline or expose Shagun's private schema.

Remediation requires **separate shared/BihariBhojan-owner authorization**, not unilateral grants/RLS changes in Shagun's deployment. Preserve existing API entries during any needed append-only Shagun configuration step; any sibling security change needs its own approved scope. Installation preservation results are recorded in [VERIFICATION.md](VERIFICATION.md); preserving a baseline does not prove it secure or audit unrelated concurrent changes. This documentation does not change permissions or authorize production promotion.

### Owner review preparation — no permission changes made

Read-only inspection of the sibling application found server-side Prisma order/contact creation and catalog reads, not a browser Supabase client or public order/message listing handler. This does **not** establish the deployed database role or exclude other consumers. Prisma creates return records, so treating the backend as INSERT-only could break legitimate submissions. Catalog caching can also hide a broken database path during a warm-page check.

Before authorizing a fix, the owner should identify the deployed effective roles, inherited/column-level grants and any other administrative, reporting, REST/RPC/view or Realtime consumers. Agree the required backend/staff operations and an isolated validation environment. A candidate narrow scope is to remove **effective anonymous/ordinary-authenticated read access to only the two private tables**, preserving the approved backend operations and unrelated catalog, Auth, Storage and Shagun behavior. Any broader grants or RLS redesign requires explicit additional review.

Closure needs both sides of the boundary: zero-row anonymous/ordinary-session probes should demonstrate the intended denial without retrieving customer rows, while representative non-production roles must still complete valid/invalid order and contact submissions, create-return handling, uncached catalog/filter/count reads and keepalive. Compare a fresh preservation baseline, review indirect access and rehearse the permission rollback. Do not reseed or reset the sibling catalog as part of permission validation. These are proposed owner checks, **not executed remediation or a safety certification**.
