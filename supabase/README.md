## Provisioning and access

- Supabase supplies `auth.users`, `auth.uid()`, the `anon`, `authenticated` and `service_role` roles, and Storage's schema. Application migrations do not create or impersonate managed Auth users.
- Shagun has no public registration. **Do not globally disable signup/anonymous sign-ins or reconfigure shared Auth without assessing BihariBhojan and obtaining operator approval.** Review password/email/recovery/redirect requirements jointly; an ordinary shared-project Auth account does not grant Shagun access. No local Auth bypass is included.
- Provision an Auth user and the matching `shagun.admin_users` allowlist row out of band. The existing `npm run admin:create` command requires a trusted interactive TTY, rejects credential arguments and hides password/confirmation input. It creates a confirmed Auth user and inserts that returned UUID, rolling back only its newly created account if allowlist insertion fails. It does not send an invitation email or promote an existing user on conflict. Alternatively create/invite the actual user in the managed dashboard, then bind that user's real UUID in an administrative allowlist insert; the safe parameterized procedure is in [../docs/DEPLOYMENT.md](../docs/DEPLOYMENT.md).
- Membership is ID-based, never derived from an email/domain. Authenticated application roles cannot modify the allowlist, including their own record. Revocation uses `is_active = false` plus managed session revocation; retain referenced review identities rather than deleting unrelated accounts.
- Public application reads use the anonymous client, not a session or service key. `public_cities`, `search_venues` and `city_facets` additionally keep strict public predicates even when called by an admin. `venue_document` is an invoker: a real active-admin session can preview a draft, but anonymous/ordinary signed-in users cannot. The application must separately guard preview routes.
- `venue_research` is never included in venue JSON. `cities.metadata` **is public** once the city is active and must not contain private provenance or secrets.
- Inventory saves and `finalize_media_upload` are security invokers with explicit membership checks and RLS, called with the freshly checked admin session. `begin_media_upload` is a narrow security definer that requires an active admin before reserving a root; authenticated clients cannot directly insert or extend reservations. Both upload RPCs are granted only to `authenticated` and reject non-admins; neither `anon` nor `service_role` receives execution permission. The lock-only queue update grant does not permit actual row changes.
- Security-definer trigger helpers are not callable by application roles. The only service-callable mutation RPCs are rate-limit consumption and aggregate event recording. Provisioning and gated server-side private-object delivery use the existing service role's deliberate RLS bypass; it must never authorize public inventory reads or reach a browser.
- Typed PostgREST/RPC access rather than an ORM/direct application connection pool is intentional. Keep `shagun_private` outside exposed PostgREST schemas; do not widen grants or disable RLS to resolve client errors.

## Consistency and editorial rules

- The private research importer is implemented in [../src/lib/actions/research.ts](../src/lib/actions/research.ts), with pure validation/mapping in [../src/lib/research-catalog.ts](../src/lib/research-catalog.ts). Only an explicitly authorized **Add researched drafts** action in a geographically matching saved city workspace may insert missing `(city_id, slug)` records. Existing records are skipped in every status, never updated/upserted. Each `save_venue` atomically saves facts, facilities and private source notes as draft/unverified, `verified_at: null`, `reviewed: false`, with null review attribution; the whole batch is not one transaction. No city edits/activation or photos are imported. All 12 prepared candidates remain unimported; see [../docs/HAZARIBAG_RESEARCH.md](../docs/HAZARIBAG_RESEARCH.md).
- Round-trip `updated_at` exactly as the database returned it, including its offset and fractional seconds. Do not parse and reserialize it through `Date`. Updates and destructive RPCs lock the row before comparing `p_expected`; a stale or absent value fails with SQLSTATE `P0001` and message `conflict`.
- Timestamps use the database transaction clock. Each application RPC is one transaction; multiple writes deliberately share a timestamp within that transaction. PGlite is single-connection, so tests exercise independent committed transactions and stale-version rejection, not genuine multi-connection lock contention.
- First launch/publication timestamps and generated IDs/audit timestamps cannot be supplied through save JSON. Triggers preserve first launch/publication across draft/unpublished/archive transitions, including direct table writes. Slugs and a venue's city association cannot change after that first milestone.
- Publishing does not require a verification claim. It does require an address, nonempty private sources and an editorial review by an active admin. Claiming verification additionally needs a supplied nonfuture check date. Editorial review never invents a check date.
- Venue factual fields, sources and facilities invalidate prior review. `save_venue` atomically stages a private draft, replaces changed associations, records explicit re-review, and only then restores the requested status/verification. Direct edits to published factual fields that bypass this sequence are rejected. Direct status-only publication may use an unchanged existing valid review. A changed verification date requires a fresh review in the same transaction.
- An active city needs a published venue at activation/reactivation, but may later become empty without being automatically deactivated. Empty public city pages must be marked noindex by the application.
- Recheck metrics include non-archived venues that are not verified, have no check date, or were checked more than 90 days ago. Counts always come from rows; public city summaries report only published totals and zero draft/recheck counts.

## Search semantics

- `simple` full-text lexemes become safely quoted prefix terms; user input is never SQL or raw tsquery syntax. Search matches venue name/locality/address **or** city name/state. No trigram extension is needed. Venue search vectors and city text expressions have GIN indexes.
- Queries are at most 100 characters, pages 1–1000, limits 1–25. Public venue pages default to 12; public cities to 24; admin lists to 25. Count and page use one shared, statement-snapshot candidate set.
- Capacity requires a recorded maximum at least as large as the guest count. Every requested facility must be recorded. Missing facts are not negative assertions.
- Budget and price sorting require a price basis. A range uses its minimum; a maximum-only estimate uses that maximum. Different bases are never compared. Capacity/price/name sorts are ascending, recent is descending `updated_at`; unknown numeric facts are last and ties use ID. Price-basis-only filtering can include an unknown price, but budget filtering cannot. Facets contain only positive recorded facts from published active inventory.

## Sitemap contract

[migrations/0003_sitemap.sql](migrations/0003_sitemap.sql) defines the invoker `sitemap_entries(p_offset integer default 0, p_limit integer default 1000)` returning `{ total, items: [{ path, updatedAt }] }`. The application uses `p_limit = 0` for counts, then fetches partitions of at most 10,000 entries, without relying on a PostgREST table row limit. Integer offsets are bounded to **0–10,000,000** and limits to **0–10,000**. Explicit SQL `NULL` for either argument and out-of-range values are rejected with SQLSTATE `22023` / `invalid_page`; a null limit cannot become an unbounded query. The database suite applies and tests this migration, including null/range guards, visibility and stable pagination.

Explicit public predicates include only **active cities with a published venue**, and **published venues in active cities**, even for admin callers. Empty cities, hidden venues and private previews are excluded. The application adds its static routes separately, reserves their space in partition zero and gates indexing on deployment configuration. The RPC is not a way to preview drafts.

## Media and cleanup

- The private bucket is **`shagun-media`**, not a shared application bucket. Shagun's policies are neutral outside that bucket; never change existing managed Storage ownership, base grants or other bucket policies to make an upload pass.
- A media row owns exactly one venue or city. Venue maximum: 24 photos; city maximum: one cover. Keys are immutable lowercase **UUIDv4 roots**, never paths or URLs. Files live at the root plus `/480.webp`, `/960.webp` and `/1600.webp`.
- The first upload is automatically the cover. Partial unique indexes and owner-row locks serialize cover selection, uploads and reordering. Deleting a cover promotes the smallest remaining `(sort_order, id)` record. Public JSON always puts the cover first.
- Photo metadata, cover, order, insert and delete touch the owner's version. Facility changes touch the venue version. Stale forms must reload instead of overwriting newly changed snapshots.
- **Reserve before Storage:** the route waits for `begin_media_upload(p_key)` to commit a durable cleanup reservation before any object upload. `ready_at` is database `transaction_timestamp()` plus **15 minutes**. Existing media roots and duplicate reservations/deletion jobs are rejected, never renewed. Direct media insertion cannot reuse a queued root.
- **Finalize atomically:** after the route confirms all three Storage uploads, session-authorized `finalize_media_upload(p_data)` locks the reservation, deletes it and inserts the media row in one transaction. Ownership, metadata or photo-limit failures roll back both writes and retain the reservation. Missing/consumed/expired reservations and deletion jobs are rejected. Database wall time is checked after reservation locking and again after insertion/owner locking, so a wait cannot extend the window. The RPC inserts metadata only; Storage HTTP success is the route's responsibility.
- **Clean only eligible, unreferenced roots:** deletion/cascade jobs default to immediate `ready_at`; abandoned upload reservations become eligible after their deadline. The current-admin-session cleanup action selects at most **25** jobs where `ready_at <=` its current UTC time, then rechecks `media_assets` for each root. A live reference or failed lookup prevents deletion. Remove all three variants before acknowledging; provider/acknowledgement failures remain retryable. Future reservations are untouched, and queued roots cannot be reused.
- Upload input is JPEG/PNG/WebP, at most **3 MiB (3,145,728 bytes)** and **40 million decoded pixels**; reject animation/invalid image bytes/SVG. Server-side decode/re-encode strips metadata and emits WebP derivatives targeting maximum widths of **480/960/1600 pixels**, preserving the oriented aspect ratio without enlargement. Saved dimensions describe the largest processed variant; a smaller source stays smaller even under a larger variant label. Upload with `upsert: false` through the active admin session after validation and an operator's rights assertion; decoding or a source URL does not prove permission. The private bucket is WebP-only and capped at **3 MiB per derivative**. Replacements use a new random root; alt text and rights credit are public-facing.
- Reservations cover interrupted/partial uploads **even when no media row was inserted**, without relying on catch-based compensation. The dashboard count includes future reservations as well as ready jobs; a zero count is not a historical/out-of-band bucket audit. These paths have local SQL/route/action tests. Real Storage failure/retry behavior remains a production gate; no automatic orphan sweeper is configured.
- Storage policies allow only active admins to select/insert/delete derivatives and reject in-place updates. Restrictive guards prevent broad preexisting policies from exposing this bucket without changing access to other buckets. Do not generate/distribute public signed URLs. Public `/media/[id]/[width]` handlers authorize ownership using anonymous RLS before trusted download/streaming; `/api/admin/media/[id]` previews require current admin authorization and private/no-store responses. Route IDs identify media rows, not storage roots.
- Unauthorized drafts must never be publicly delivered or cached. Already-published image responses can remain in the public CDN for at most 60 seconds; visitor downloads and external caches cannot be recalled. Unpublishing is not a promise to erase prior public copies.

## Boundary differences from the hand-maintained TypeScript contract

SQL constraints remain authoritative at the PostgREST boundary. Contracts live in [../src/lib/db/database.types.ts](../src/lib/db/database.types.ts), with input checks in [../src/lib/validation.ts](../src/lib/validation.ts) and the Server Actions. Do not assume every shared validator is identical to PostgreSQL.

- PostgreSQL additionally stores the generated `venues.search_document`, which is intentionally omitted from the hand-maintained `Venue` interface and every venue document. Database-generated types will include it; keep it out of writable/public DTOs.
- `Photo.credit` is nullable in the shared interface, but new database rows require a nonempty 5–300-character rights note. `width` and `height` must be integers in 1–20000. Root keys must be UUIDv4, matching `crypto.randomUUID()`.
- Verification input accepts a valid nonfuture ISO `YYYY-MM-DD` (interpreted as midnight UTC) or an ISO timestamp with an explicit `Z`/offset and at most six fractional digits. PostgreSQL shortcuts such as `now` and `infinity` are rejected. Although the shared `venueSchema` alone has a broader `Date.parse` check, the **existing, tested** guard in [../src/lib/actions/venues.ts](../src/lib/actions/venues.ts) rejects fallback date strings and invalid calendar dates before the RPC, and requires sources even for a reviewed draft. Ordinary saves do not allow fallback date syntax; callers reusing only the shared schema must also enforce the stricter boundary.
- Metadata is a scalar-valued JSON object capped at **3000 UTF-8 bytes in PostgreSQL's formatted JSON representation**. The shared city schema checks JavaScript string length, while the **existing, tested** guard in [../src/lib/actions/cities.ts](../src/lib/actions/cities.ts) also checks UTF-8 bytes of `JSON.stringify`, rejecting over-budget multi-byte input before writing. PostgreSQL's formatting/escaping can still make its representation larger: its byte check is the final authority. Keep metadata comfortably below the cap; action acceptance is not a guarantee for a near-limit object.
- Table ACLs deliberately expose only the current user's allowlist row and deny all allowlist writes to authenticated JWTs. Facilities are fixed to the shared nine-code vocabulary; changes to the vocabulary require a coordinated schema/TypeScript migration.
- Rate keys accept 1–200 characters from letters/digits/colon/underscore/hyphen. The backend must generate HMAC-only keys, not raw addresses. Allowed limits are 1–10000 attempts and 1–86400 seconds; cleanup removes at most 100 expired buckets per call. Events retain the 90-day boundary and clean at most 500 older aggregate rows per valid call. Invalid/nonpublic event contexts are ignored; malformed event names or missing required venue IDs are errors.
